# Play Store submission process for Vinho (Android)

This is the Android companion to `../vinho-ios/APP-STORE-SUBMIT-PROCESS.md`. It
takes Vinho from source to a Google Play draft release using the automated
pipeline in `scripts/release-android.sh`, so your only manual work is the
account-gated Play Console steps.

Package name: `com.strategicnerds.vinho` · Min SDK 26 · Target SDK 35.

The automated pieces are already in place:
- `apps/vinho-android/app/build.gradle.kts` — Triple-T Play Publisher plugin,
  conditional release signing, `play { track="internal"; releaseStatus=DRAFT }`.
- `scripts/sync-android-config.sh` — materializes config + keystore + Play
  service-account JSON from Doppler.
- `scripts/release-android.sh <track>` — bumps versionCode, builds a signed AAB,
  uploads it as a **draft** to the chosen track.

What only you can do (account-gated): create the app in Play Console, accept
agreements, generate the signing keystore, and create the publisher service
account. Everything below walks through those, then hands off to the script.

---

## Phase 1 — Google Play developer account (one-time)

1. Enrol in the Google Play Console at https://play.google.com/console
   ($25 one-time fee). Personal or organization account.
2. Complete identity verification (D-U-N-S if organization; can take a few days).
3. Accept the Developer Distribution Agreement and complete the account details.

## Phase 2 — Create the app

1. Play Console → **Create app**.
   - App name: **Vinho**
   - Default language: English (United States)
   - App or game: App
   - Free or paid: **Free**
   - Accept the Developer Program Policies + US export law declaration.
2. After creation you land on the app dashboard. The package
   `com.strategicnerds.vinho` is claimed on the first AAB upload (Phase 6).

## Phase 3 — Store listing content

Under **Grow → Store presence → Main store listing**:
- **App name**: Vinho
- **Short description** (≤80 chars): e.g. "Your personal wine tasting journal — scan, rate, and remember every bottle."
- **Full description** (≤4000 chars): features — scan a label to auto-identify
  the wine, rate and take tasting notes, see your collection on a map, get
  recommendations, share tastings with friends.
- **App icon**: 512×512 PNG, 32-bit, no alpha → `store-assets/play-icon-512.png`
  (generated by Phase 6b of the build plan).
- **Feature graphic**: 1024×500 PNG/JPG → `store-assets/play-feature-1024x500.png`.
- **Phone screenshots**: 2–8, 16:9 or 9:16, min 320px, max 3840px →
  `store-assets/screenshots/` (Phase 6c).

## Phase 4 — Required policy declarations

Under **Policy → App content**:
- **Privacy policy**: https://www.vinho.dev/privacy
- **Data safety**: declare what Vinho collects and sends to Supabase / PostHog:
  - Personal info: **email address** (account) — collected, not shared, required.
  - Photos: **wine label photos** (scan) → Supabase Storage — collected, not shared.
  - Location: **approximate/precise** (tasting location, map) — collected, optional.
  - App activity / analytics: **PostHog** product analytics — collected, not shared.
  - Data is encrypted in transit; users can request deletion in-app (account deletion).
- **Content rating**: complete the IARC questionnaire (Vinho is an alcohol-
  related reference/journal app — expect a rating that requires an alcohol
  disclosure; answer truthfully: user-generated content = no, alcohol reference = yes).
- **Target audience**: 21+ (alcohol). Do NOT mark as appealing to children.
- **Ads**: No ads (unless you add them).
- **Government apps / financial / health**: No.

## Phase 5 — Signing + publisher API credentials (put these in Doppler)

The pipeline reads everything from the `vinho` Doppler project. Add these keys
(config `prd`):

### 5a. Release upload keystore

Generate a keystore (do this ONCE and keep the backup safe — losing it means you
can't update the app without Play's key-reset process):

```bash
keytool -genkeypair -v \
  -keystore vinho-release.jks \
  -alias vinho -keyalg RSA -keysize 2048 -validity 10000 \
  -storepass '<STORE_PASSWORD>' -keypass '<KEY_PASSWORD>' \
  -dname "CN=Strategic Nerds, O=Strategic Nerds, C=US"

# base64-encode it for Doppler (single line):
base64 -i vinho-release.jks | tr -d '\n' | pbcopy
```

Set in Doppler (`vinho`/`prd`):
- `ANDROID_RELEASE_KEYSTORE_BASE64` — the base64 string above
- `ANDROID_RELEASE_STORE_PASSWORD` — `<STORE_PASSWORD>`
- `ANDROID_RELEASE_KEY_ALIAS` — `vinho`
- `ANDROID_RELEASE_KEY_PASSWORD` — `<KEY_PASSWORD>`

Recommended: also enrol in **Play App Signing** (Play Console → Release → Setup →
App signing) so Google manages the app signing key and your upload key above is
only the upload credential.

### 5b. Play publisher service account (for automated upload)

1. Play Console → **Users and permissions → Invite new users**, or use the API
   access flow: Play Console → **Setup → API access**.
2. Create/link a Google Cloud project, then create a **service account** in
   Google Cloud IAM. Download its JSON key.
3. Back in Play Console → API access → grant that service account access, with
   at least **Release to testing tracks** + **Manage store presence** for the
   Vinho app.
4. Put the JSON into Doppler as a single value:
   - `ANDROID_PLAY_SA_JSON` — the full contents of the service-account JSON.

### 5c. Build config secrets (should already exist for the app to run)

`SUPABASE_URL`, `SUPABASE_ANON_KEY`, `MAPS_API_KEY`, `POSTHOG_API_KEY`,
`POSTHOG_HOST` (and optionally `VINHO_API_BASE_URL`).

## Phase 6 — First upload (automated)

Play requires a **manual first upload** to claim the package on some accounts;
the script performs a normal upload which satisfies this. From the repo root:

```bash
# Syncs config/keystore/SA JSON from Doppler, bumps versionCode, builds a signed
# AAB, and uploads it to the internal testing track as a DRAFT.
./scripts/release-android.sh internal
```

Then in Play Console → **Testing → Internal testing**: review the draft release,
add release notes, and **roll it out** to internal testers. Add testers under
the Internal testing → Testers tab (an email list or Google Group).

## Phase 7 — Promote to production

Google Play requires **closed testing with ≥12 testers for ≥14 days** before a
personal developer account can access production. Run internal/closed testing to
satisfy this, then:

```bash
./scripts/release-android.sh production   # uploads a production DRAFT once eligible
```

Complete the production roll-out (staged %) in Play Console.

## Track cheat-sheet

| Command | Track | Use |
|---|---|---|
| `./scripts/release-android.sh internal` | Internal testing | Fastest, up to 100 testers, no review wait |
| `./scripts/release-android.sh alpha` | Closed testing | Counts toward the 12-tester/14-day gate |
| `./scripts/release-android.sh beta` | Open testing | Public opt-in testing |
| `./scripts/release-android.sh production` | Production | Live (after the gate clears) |

Every upload lands as a **DRAFT** (`releaseStatus=DRAFT` in build.gradle.kts) —
nothing goes live until you roll it out in Play Console. `SKIP_VERSION_BUMP=1`
retries a failed upload with the same build; `SKIP_CONFIG_SYNC=1` uses the
existing `local.properties` as-is.

## Troubleshooting

- **"Package not found" on first upload**: some accounts require the very first
  AAB to be uploaded manually in Play Console (Create app → upload). Do that
  once, then `release-android.sh` works for all subsequent releases.
- **"Version code already used"**: the bump didn't run or a prior upload used
  that code. Re-run without `SKIP_VERSION_BUMP`.
- **Signing errors**: confirm `ANDROID_RELEASE_KEYSTORE_BASE64` decodes to a
  valid `.jks` and the passwords/alias match. `sync-android-config.sh` writes
  them into `apps/vinho-android/local.properties` (gitignored).
- **Auth to Play fails**: the service account needs the app granted in Play
  Console API access, and the Google Play Android Developer API enabled in the
  linked Cloud project.
