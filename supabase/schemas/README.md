# Declarative schemas

These files describe the desired state of the database. `supabase db diff` applies
them to a shadow database, compares it against your local database, and writes the
difference out as a migration.

## Workflow

```bash
# 1. Edit the schema files here (never Studio, never the SQL editor)
# 2. Generate a migration from the change
supabase db diff -f describe_your_change

# 3. Apply locally and verify
supabase db reset

# 4. Ship
supabase db push
```

The golden rule: **edit these files, not the database.** Changes made directly in
Studio or the SQL editor are invisible to `db diff` and will be silently reverted
the next time someone generates a migration.

## Files

| File | Contents |
|---|---|
| `10_public.sql` | The `public` schema: tables, functions, views, indexes, triggers, RLS policies, grants. Generated by `supabase db dump --local`. |
| `20_storage_policies.sql` | RLS policies on `storage.objects`. |

Order matters and is set by `schema_paths` in `supabase/config.toml`. Files run in
the order listed there, which is why they are numbered.

## Why storage policies are a separate file

`supabase db dump` does not include the `storage` schema. Without
`20_storage_policies.sql`, the shadow database has no storage policies, so `db diff`
concludes all nine should be deleted and emits:

```
drop policy "Users can view their own scans" on "storage"."objects"
...
```

Applying that would undo the fix that scopes each user's scans and avatars to their
own folder, making every user's uploads readable by anyone. `storage.objects` itself
is created by the storage extension in the base image, so that file declares only
the policies on it, not the table.

If you ever see `db diff` proposing to drop storage policies, do not apply it. It
means this file has drifted from the database.

## What the diff engine cannot track

Per the [Supabase docs](https://supabase.com/docs/guides/local-development/declarative-database-schemas),
these must stay in hand-written migrations under `supabase/migrations/`:

- DML: `insert`, `update`, `delete`
- View ownership, `security_invoker` settings, materialized views, column type changes
- `alter policy` statements and column privileges
- Schema privileges, comments, partitions, `alter publication`, `create domain`
- Duplicate grant statements arising from default privileges

This project uses several of them. `user_wine_stats_materialized` is a materialized
view, there are 32 `comment on` statements, and the function-grant lockdown that
restricts `SECURITY DEFINER` functions to `service_role` is expressed as grants. All
of that is already captured in `10_public.sql` as current state, but if you change
any of it, write the migration by hand and then refresh these files so they stay in
sync.

Everything under `supabase/migrations/` remains the source of truth for what has
actually been applied to production. Declarative schemas are how new migrations get
written, not a replacement for the migration history.

## Keeping these files current

After applying a hand-written migration, refresh the dump so the declarative state
matches reality:

```bash
supabase db reset
supabase db dump --local -f supabase/schemas/10_public.sql
supabase db diff   # must print "No schema changes found"
```

That last check is the acid test. If it prints anything else, the schema files and
the database disagree and the next generated migration will be wrong.
